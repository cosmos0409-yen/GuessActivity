# 全場搶答系統（Kahoot 式）— 規劃

> 目的：在闖關猜謎開始前，讓現場 140 多人用手機即時搶答，選出前 3 名進入闖關。
> 狀態：**規劃中，等使用者核可與 Supabase 帳號**（2026-09-13）

## 已定案（使用者 2026-09-13 決定）
| 項目 | 決定 |
|---|---|
| 做法 | 自己做，即時連線用 **Supabase** 免費方案（同時連線 200 人、每月 200 萬則訊息） |
| 題數與時間 | **10 題 × 每題 20 秒** |
| 題庫 | 同一份 Google 試算表，另開「**搶答題**」分頁，不消耗闖關題目 |
| 圖片 | 使用者提供圖檔，放進專案的 `public/kahoot/`，隨 GitHub Pages 一起發布 |

## 為什麼不用 Apps Script 或 Firebase（研究結論，來源見 scratchpad 的 kahoot-research.md）
- Apps Script：同時只能執行 30 個請求，撐不住 140 人同時作答
- Firebase 即時資料庫：免費方案同時連線上限 100 人
- 現成服務（Kahoot、Wayground 等）：免費方案的人數上限都不確定，而且偏低

## 架構
```
Google 試算表「搶答題」分頁 ──(主持人頁開場讀一次 CSV)──▶ 主持人頁 host.html
                                                          │ 建立場次、推送題目
                                                          ▼
                                                  Supabase（即時連線＋資料庫）
                                                          ▲
觀眾手機 join.html ──(輸入 PIN 與暱稱、點色塊作答)────────┘
```
- **同一個 repo、同一個 Pages 網址**：新增 `host.html`（主持人）與 `join.html`（觀眾），共用院徽色系。
- **手機只顯示 4 個色塊加形狀**（紅▲、藍◆、黃●、綠■），題目與圖片只在大螢幕上顯示。
- **防作弊**：正確答案只存在觀眾讀不到的資料表；作答時間由**伺服器**計算（伺服器收到答案的時間減掉題目開始的時間），不信任手機的時鐘。
- **計分**（Kahoot 公式）：答對得 `1000 × (1 − 作答秒數 ÷ 20 ÷ 2)` 分，答錯 0 分；同分時先比答對題數，再比總作答時間。
- **前 3 名帶進闖關**：頒獎台上有一個按鈕，可以把 3 個名字存到同一個瀏覽器，闖關遊戲的大廳可以直接選。

## 資料表（Supabase）
| 表 | 內容 | 觀眾能讀嗎？ |
|---|---|---|
| games | 場次、PIN、狀態、目前題號、題目開始時間 | 能（只能讀狀態） |
| players | 暱稱、分數 | 能（排行榜） |
| answers | 誰、第幾題、選什麼、伺服器時間、得分 | 不能（只能透過作答函式寫入） |
| answer_keys | 各題正解 | **不能** |
- 作答透過資料庫函式 `submit_answer` 寫入，由函式負責計時與計分；每人每題只能答一次。
- 主持人操作需要一組「主持人密碼」，建立場次時產生，存在主持人的瀏覽器裡。

## 主持人流程
1. 開啟 `host.html` → 讀取搶答題 → 建立場次 → 大螢幕顯示 **PIN＋QR code**，以及即時的加入人數與暱稱牆（可以踢掉不當暱稱）。
2. 按開始 → 每題：題目與圖片、20 秒倒數、已作答人數 → 揭曉答案分布 → 前 5 名排行榜。
3. 10 題結束 → 前 3 名頒獎台動畫 → 「帶進闖關」。

## 「搶答題」分頁欄位
`id | 題目 | 圖片檔名 | A | B | C | D | 正解 | 秒數(選填，預設 20) | 狀態(上架／待審)`

## 風險
1. **現場網路**：140 支手機同時連線，要事先確認 Wi-Fi，或請大家用行動網路；活動前會用腳本模擬 150 個連線做壓力測試。
2. **Supabase 免費專案太久沒使用可能會被暫停**（待確認），活動前幾天要登入確認。
3. 暱稱可能不當：主持人可以踢人；只收暱稱，不收任何個資。

## 需要使用者操作
1. 註冊 Supabase，建立專案（區域選 Tokyo 或 Singapore），把 **Project URL** 與 **anon／publishable key** 給 Claude（這兩個本來就會放在前端，可以公開；**不要**給 service_role 或 secret key）。
2. 在 Supabase 的 SQL Editor 貼上 Claude 提供的建表 SQL 並執行。
3. 提供圖片題的圖檔。

## 執行階段
- Phase K1：Supabase 建表 SQL＋資料庫函式（計時、計分、防重複作答）＋權限設定
- Phase K2：觀眾頁 `join.html`（加入、等待、作答、看自己的名次）
- Phase K3：主持人頁 `host.html`（讀題庫、建立場次、PIN／QR、出題、排行榜、頒獎台、帶進闖關）
- Phase K4：壓力測試（模擬 150 個連線）、手機實測、斷線重連
- Phase K5 — 更新規格文件
  - `doc/handover.md` — 更新（新增搶答系統章節）
  - `README.md` — 更新（搶答操作說明）
  - `CLAUDE.md` — 更新（新增 Supabase 相關約束：不能 commit secret key、正解不能讓觀眾讀到）
